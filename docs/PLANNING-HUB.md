### 0.3 Step 3 Reference Foundation 대조 (2026-09-16)

§4 Step 3 은 공식 기준의 존재를 묻습니다. **정책 요율의 존재 여부**와 **계산기가 다루는 개념·입력
정의·사용 목적을 뒷받침하는 공식 근거의 존재 여부**를 구분해 대조했습니다.

공식 자료의 권장 기간·비율을 사이트 기본값으로 가져오지 않습니다. 출처가 있다는 이유로 자체
산식을 공식 산식이라고 표현하지도 않습니다.

**근거를 4계층으로 구분합니다. 이 구분은 이번 기획의 검토 편의를 위한 것이며, Locked 공통
아키텍처에 새로운 예외 규칙을 두는 것이 아닙니다.** 공통 기준 §4 Step 3 의 해석을 바꾸지
않으며, 다른 플랫폼에 이 표를 적용하지 않습니다.

공식 자료가 자체 분류·산식과 같은 형태이기를 요구하지는 않습니다. 각 계층에 요구되는 것이
다릅니다.

| 계층 | 내용 | 요구되는 것 |
|---|---|---|
| ① 개념·계약상 사실 | 공식 자료가 직접 뒷받침하는 용어 정의, 법·약관이 정한 사실 | **공식 출처 필요.** 없으면 그 주장을 하지 않음 |
| ② 입력 분류 | 지출 7항목 같은 자체 구성 | 공식 분류와 일치할 필요 없음. **화면에서 공식 분류인 것처럼 쓰지 않음** |
| ③ 수학적 산식 | 사칙연산·복리 계산 | 공식 근거 대상이 아님. **손 검산으로 검증** |
| ④ 사용자 가정 | 대비 개월, 이사비 금액 등 | 사이트가 값을 제시하지 않음. **입력받고 그 사실을 표시** |

> ⚠️ **'자체 가정'이라는 이름표가 근거 공백을 해소하지 않습니다.** ①에 해당하는 주장을 ④로
> 옮겨 적는 것은 회피입니다. 계층을 옮길 때는 그 주장을 화면에서 실제로 하지 않아야 합니다.

> ⚠️ **수학적 정확성 검증과 모델 검증은 다릅니다.** ③은 "산식이 그 정의대로 정확히 계산되는가"
> 이고, 손 검산·단위 테스트로 확인합니다. 이것이 통과해도 "그 모델의 가정과 적용 범위가
> 사용자 상황에 타당한가"는 별개 문제이며 ①·④ 영역입니다. 3.2절 산식 검산은 ③을 통과시킨
> 것이지 모델 타당성을 검증한 것이 아닙니다.

| 뒷받침하지 않는 범위 | ① `흑자액 = 처분가능소득 − 소비지출` 계산식은 가계동향조사 보도자료 **본문 서술로만 확인**했고 통계 표준용어 원문 정의는 미확인(404·robots 차단) ② 통계청 소비지출 12대 비목과 우리 7항목은 일치하지 않으며 **7항목 분류를 뒷받침하는 공식 근거는 없음** ③ 가계동향조사는 **가구 단위 표본조사 개념**이며 개인 가계부 산식이 아님 ④ 사업·프리랜서 소득은 원천징수 구조가 달라 '세후'의 의미가 다름 |

#### 비상자금 — 개념 근거 확인 (해외 공식 기관 교육자료, 2026-09-16)

| | 내용 |
|---|---|
| 공식 자료 | **미국 소비자금융보호국(CFPB)** 『An essential guide to building an emergency fund』 — https://www.consumerfinance.gov/an-essential-guide-to-building-an-emergency-fund/ |
| 자료 성격 | 정부기관이 발행한 **소비자 금융교육 자료**. 법규가 아니며 **한국의 법적·정책적 기준도 아닙니다** |
| 직접 뒷받침 ① 정의 | *"An emergency fund is a cash reserve that's specifically set aside for unplanned expenses or financial emergencies."* → 비상자금 = **예상하지 못한 지출이나 재정적 비상 상황에 대비해 따로 떼어 둔 현금 준비금** |
| 직접 뒷받침 ② 용도 | *"Some common examples include car repairs, home repairs, medical bills, or a loss of income."* → 차량 수리 · 주택 수리 · 의료비 · **소득 상실** |
| 직접 뒷받침 ③ 금액 기준 | *"Think about the most common kind of unexpected expenses you've had in the past and how much they cost. This may help you set a goal…"* → **특정 금액도, 특정 개월 수도 제시하지 않습니다.** 개인의 과거 경험에 따라 목표를 정하라고 안내합니다 |
| 정합 | ③은 5.2절의 "대비 개월에 사이트 기본값을 두지 않는다"는 결정과 방향이 같습니다. 다만 이 자료를 근거로 우리 결정을 정당화하는 것이 아니라, **우리 결정이 이 자료와 어긋나지 않는다는 확인**입니다 |

**⚠️ 우리 산식은 이 자료가 뒷받침하지 않습니다**

`월 필수지출 × 사용자 지정 개월 − 사용 가능한 자금` 을 CFPB 의 공식 산식으로 인용하지 않습니다.
CFPB 가 제시하는 접근은 **과거에 실제로 겪은 돌발지출의 종류와 규모를 떠올려 목표를 정하는**
방식이며, 우리 산식과 다릅니다.

**⚠️ 우리 계산기는 제한된 모델입니다**

CFPB 가 드는 용도 네 가지 중 우리 계산기가 다루는 것은 **소득 상실(loss of income) 대비**
한 가지입니다. 정확히는 *"사용자가 정한 기간 동안의 필수지출을 얼마로 대비할 것인가"* 를
계산합니다.

| 용도 | 우리 계산기 |
|---|---|
| 소득 상실 대비 | **다룸** — 사용자가 정한 기간 × 월 필수지출 |
| 차량 수리 · 주택 수리 · 돌발 의료비 | **다루지 않음** — 사건별 금액이라 기간 × 월 지출로 산정되지 않음 |

결과와 이용 안내에 이 범위를 명시합니다. **돌발 의료비·수리비까지 모두 산정하는 것으로
표현하지 않습니다.**

| 뒷받침하지 않는 범위 | ① 우리 산식 ② 돌발 지출 유형별 금액 ③ 한국의 소득 공백 제도(실업급여 등) — v1 제외 유지 ④ 한국 기준 적정 수준 |

## 3. 착수 차단 항목 해소 — `/finance/goal-savings` 실측 (2026-09-16)

### 3.1 판정: **중복**

`src/lib/finance.ts` 4절이 이미 3모드 역산기입니다.

```
targetToMonthly            목표금액 + 기간       → 월 납입액
monthlyToMonths            월 납입액 + 목표금액  → 필요 기간
monthlyAndMonthsToAmount   월 납입액 + 기간     → 도달 금액
```

기획 단계의 자금계획 목표자금 2모드가 앞의 두 개와 그대로 일치합니다.

"금융상품 변수가 핵심이면 분리 근거가 생긴다"는 판정 기준에 대한 답도 코드에 이미 있습니다.

- 엔진이 `i === 0` 을 정식 분기로 처리합니다 (`monthlyAnnuityFV`, `goalRequiredMonthly`, `goalRequiredMonths` 전부)
- 페이지 FAQ 4번: *"보수적으로 잡고 싶다면 연이율에 0을 넣어 이자 없이 순수 납입만으로 계획을 세울 수 있습니다."*
- 홈 `PURPOSE_GROUPS` 의 `cash` 그룹 주석: *"저축의 출발점은 '얼마를 모아야 하나'이므로 목표 저축을 대표로 둔다"*

→ 무이율 순수 산술 목표자금은 **이미 지원 중이고 안내까지 나가 있습니다.** 신규 페이지를 만들면 같은 질문에 답하는 페이지가 두 개가 됩니다.

### 3.2 다만 실제 공백이 하나 있습니다 — 조용한 오답 경로

세 모드 전부 **현재 보유자금 입력이 없습니다.** `FIELDS` 는 `target / monthly / months / rate` 네 개뿐입니다.

```
목표 3,000만원 · 현재 1,000만원 · 24개월  →  월 83.3만원
```

이 케이스를 못 풉니다. 사용자가 손으로 2,000을 빼서 넣어야 하는데, **연이율이 0이 아니면 그 계산이 틀립니다.** 보유한 1,000만원도 기간 내내 이자가 붙는데 그게 빠지기 때문입니다. 필요 월 납입액이 **과대** 산정되고 화면에는 아무 경고가 없습니다.

**오차 크기 (2026-09-16 검산)**

대상 오류는 **목표금액에서 보유자금만 단순 차감하고, 보유자금의 이자 성장을 누락한 경우**입니다.
보유자금을 아예 차감하지 않은 경우의 오차와는 다릅니다.

| 전제 | 값 |
|---|---|
| 목표금액 / 보유자금 / 기간 | 3,000만원 / 1,000만원 / 24개월 |
| 연이율 | 3% — 월이율 0.25% 로 적용 |
| 금리 적용 대상 | 월 납입액과 **보유자금에 동일 금리** 적용 |
| 납입 방식 | 기말 납입 월복리 (기존 `monthlyAnnuityFV` 와 동일) |

```
정확 (보유자금의 이자 성장 반영)        월 78.46만원
보유자금만 단순 차감 (이자 성장 누락)    월 80.96만원
                                      → 월 2만 5천원 과대
                                      → 24개월 납입액 합계 60만원 과대
```

보유자금 비중이 크거나 기간이 길수록 벌어집니다. `PR-X` 의 우선순위 판단 근거입니다.

FAQ 4번이 무이율 경로를 권하고 있어 오히려 이 함정으로 유도되는 구조입니다.

**처리**: 별도 PR로 분리 — `feat(finance): 목표 저축 계산기 현재 보유자금 반영` (7절 PR-X).
이 허브의 선행 조건이 아닙니다. 현재 **보류** 상태입니다.

## 4. 허브 생성 판정

### 4.1 기준 충족

확정한 기준은 "독립 완성 가능한 계산기 최소 3개". 목표자금이 빠진 뒤 1차 착지는

```
월 잉여자금 · 비상자금 · 이사자금 = 3개  →  조건 충족
```

이사자금을 1차로 올린 근거: 실투자금 계산기(매수)의 **임차 버전**에 해당해 독립 계산 의도가 가장 뚜렷하고, 부동산 허브의 전세·월세 계산기 4종과 링크 밀도가 높습니다.

### 4.2 중복 없음 확인

`비상자금` `생활비` `잉여` `가처분` — 저장소 전체 검색 결과 계산기 0건.
(`InitialCostCalc` 의 "이사비·수리비" 는 기타 비용 입력 힌트 문구, 블로그 1건은 본문 표)

### 4.3 이사자금의 허브 소속 — 부동산이 아니라 자금계획

기존 판정 기준("핵심 입력값이 돈인가 물건인가")으로는 실투자금과 이사자금이 구분되지 않습니다. 둘 다 돈입니다. 추가 기준을 둡니다.

> **거래 대상 자체가 부동산인가, 생활 이벤트인가.**
> 실투자금 = 매수라는 부동산 거래. 이사자금 = 부동산 계약 + 이사·가전 등 생활비용.

이사자금은 후자 비중이 크므로 자금계획 소속입니다. 단 **부동산 허브에서 역링크 필수** — 전세대출·월세 vs 전세 페이지에서 이사자금으로 연결합니다.

### 4.4 ⚠️ Header 는 4번째가 아니라 5번째 항목이 됩니다

`NAV_GROUPS` 실측:

```
대출 계산기 (10)  ·  부동산 계산기 (7)  ·  금융 계산기 (10)  ·  금융 가이드
```

자금계획을 넣으면 **네비게이션 항목 5개**입니다. 환전 계산기 때 "계산기 1개를 위해 4번째 허브를 만들면 Header 가 무거워진다"고 판단해 `/finance` 편입을 골랐던 그 부담이, 이번에는 한 칸 더 큰 상태에서 발생합니다.

착수 전 확인: 모바일 네비(`mobileGroup` 아코디언)에서 5그룹이 접힌 상태로 수용 가능한지 브라우저 확인.

### 4.5 홈 `PURPOSE_GROUPS` 에 4번째 목적 그룹이 필요합니다

홈이 이미 목적 기반 3분류로 재편되어 있습니다.

```
limit  얼마나 빌릴 수 있나    primary: dsr
house  집을 사거나 임대 투자   primary: initialCost
cash   저축하고 현금 관리      primary: goalSavings
```

자금계획은 여기에 들어갈 자리가 없습니다. 4번째 그룹(가칭 `plan` — "얼마가 필요한가")을 추가해야 하며, `cash` 그룹의 primary 가 `goalSavings` 라는 점이 3.1절 중복 판정을 홈 쪽에서 한 번 더 확인해 줍니다.

> 겹칩니다.

> 이 점검은 0.3절에서 처분가능소득 정의를 대조하며 드러난 것입니다. 통계상 처분가능소득은
> 이전지출까지 공제한 개념이라 **우리 입력값과 같지 않습니다.** 화면에서 두 용어를 같은 것으로
> 쓰지 않습니다.

**출력**: 월 잉여자금 · 연 잉여자금 · 총 지출 · 소득 대비 지출 비율(%)

> ⚠️ 소득 대비 지출 비율은 **수치만** 표시합니다. "적정", "높음", 색상 경고 모두 금지.
> 전월세 전환율 계산기가 법정 상한 초과를 사실로만 표시하고 위법 판정을 하지 않는 방식과 동일합니다.

**예외**: 소득 미입력 시 결과 미표시 / 잉여자금 음수는 **정상 표시** (적자는 실제 상태) + "지출이 소득을 넘습니다" 사실 안내. `PropertyYieldCalc` 의 `isInvestedNegative` 패턴 재사용.

**정책 데이터**: 없음.

### 5.2 비상자금 계산기

| 항목 | 내용 |
|---|---|
| 사용자 질문 | "소득이 끊기면 얼마가 필요한가 / 얼마나 버티나" |
| 모드 | 대비기간 기준 / 소득공백 기준 |

```
모드 A  대비기간 기준   월 필수지출 × 대비 개월            → 필요 비상자금
                        ( − 현재 보유자금 → 추가 필요자금 )
모드 B  소득공백 기준   현재 보유자금 ÷ 월 필수지출        → 버틸 수 있는 개월
```

두 모드는 같은 식의 역함수입니다. DSR 계산기의 확인/추정 2모드 선례를 그대로 따릅니다. 기획 단계의 "소득공백 생활자금"을 별도 페이지로 만들지 않고 모드 B 로 흡수했습니다 — 산식이 동일한데 페이지를 쪼개면 서로 카니발라이즈됩니다.

**⚠️ 모델 범위를 결과와 안내에 명시합니다**

이 계산기는 비상자금의 여러 용도 중 **"사용자가 정한 기간의 필수지출 대비"** 한 가지를 계산합니다
(0.3절). 고정 노출 문구의 취지:

> 소득이 없는 기간의 필수지출을 얼마로 대비할지 계산합니다. 차량·주택 수리나 갑작스러운 의료비
> 같은 사건별 지출은 이 계산에 포함되지 않습니다.

**돌발 의료비·수리비까지 모두 산정하는 것으로 표현하지 않습니다.**

> ⚠️ **대비 개월 수에 기본값을 두지 않습니다.** "6개월이 적당합니다" 류 규범 금지.
> 근거는 존재하지 않는 ADR 이 아니라 사이트 무판정 선례입니다 (9.3절 참조).
> CFPB 자료도 특정 개월 수를 제시하지 않으나, 그 자료를 근거로 우리 결정을 정당화하지는
> 않습니다 — 어긋나지 않는다는 확인일 뿐입니다.

**예외**: 월 필수지출 미입력 시 결과 미표시 / 모드 B 에서 보유자금 0 → 0개월 정상 표시.

**정책 데이터**: 없음. 실업급여 산정은 2.2절에 따라 제외.

### 5.3 이사자금 계산기

| 항목 | 내용 |
|---|---|
| 사용자 질문 | "이사하는 데 현금이 추가로 얼마 드나" |
| 성격 | 실투자금 계산기(매수)의 임차 버전 |

```
새 보증금
 −  기존 보증금 회수액
 +  이사비 + 임대차 중개보수 + 가전·가구 + 기타 초기비용
 =  추가 필요자금
```

**출력**: 추가 필요자금 · 총 이사 부대비용 · 보증금 차액

#### ⚠️ 이 허브의 유일한 정책 데이터 이슈

`src/lib/policy/brokerage.ts` 의 `unsupported` 에 **"주택 임대차 중개보수"** 가 명시되어 있습니다. 현재 검증된 것은 주택 매매·교환 6구간 상한요율뿐입니다.

임대차는 요율표가 다를 뿐 아니라 **거래금액 산정 방식 자체가 다릅니다** — 월세는 보증금 + 월차임 환산액이고, 합계가 일정 금액 미만이면 환산 배수가 달라집니다. 매매 요율표를 재사용할 수 없습니다.

**v1 처리**: 중개보수는 **사용자 직접 입력**. 자동 산정하지 않습니다.
임대차 요율표 확정은 별도 정책 PR 로 분리합니다 (7절 PR-Y). 근거 없는 수치를 넣는 것이 이 계산기의 가장 큰 위험입니다.

**⚠️ 조건부 계산임을 명시합니다**

기존 보증금 회수액은 **사용자가 입력한 예상액**입니다. 계산기는 그 금액이 실제로, 제때 반환된다고
전제하지 않으며 반환 여부·시점·감액 가능성을 판단하지 않습니다. 결과 문구와 이용 안내에
다음 취지를 고정 노출합니다.

> 입력하신 회수 예상액을 그대로 반영한 금액입니다. 보증금의 실제 반환 여부와 시점은 계약·분쟁
> 상황에 따라 달라지며 이 계산기는 이를 판단하지 않습니다.

**예외**: 새 보증금 미입력 시 결과 미표시 / 기존 보증금 > 새 보증금이면 추가 필요자금 음수 → **정상 표시** ("보증금이 줄어 회수액이 발생합니다").

### 5.4 독립생활 자금 계산기 (2차)

```
초기 보증금 + 이사비 + 생활 집기 + (월 생활비 × N개월)  =  독립 초기자금
```

5.1 과 5.3 의 조합입니다. 두 계산기가 배포되어 실제 입력 축이 굳은 뒤 착수합니다.

## 8. 정확성·정책·테스트

### 8.1 이 허브의 성격

계산기 대부분이 사칙연산이라 **`verifiedAt` 관리 대상이 사실상 없습니다.** 재검증 트리거 표에 올라가는 항목이 0건인 첫 허브입니다.

유일한 예외가 임대차 중개보수이며, v1 에서 직접 입력으로 처리해 예외를 만들지 않습니다.

### 8.2 무판정 원칙 — 이 허브에서 특히 위험한 지점

| 지점 | 금지 |
|---|---|
| 소득 대비 지출 비율 | "적정/과다" 표현, 경고 색상 |
| 비상자금 대비 개월 | 기본값, "권장", "일반적으로 6개월" |

| 이사자금 | 이사 시점·방식 권유 |

### 8.3 ⚠️ D7 은 이 저장소에 존재하지 않습니다

기획 단계에서 "D7 철학"을 근거로 인용했으나, **현재 저장소에 `DECISIONS.md` 파일이 없습니다.** 설계 결정 표기는 `docs/CALCULATOR-EXPANSION.md` 안의 D1~D4(LTV)·E1~E4(실투자금)뿐이고 D5 이상은 확인되지 않습니다.

> 확인 범위: 2026-09-16, 로컬 저장소의 `git log --all`(로컬 `refs/heads` + 마지막 fetch 시점의
> `refs/remotes/origin`)로 확인 가능한 이력 기준. 해당 경로의 추가·삭제 이력은 확인되지
> 않았습니다. 아직 fetch되지 않은 원격 전용 브랜치와 별도·이전 저장소는 확인하지 않았으므로,
> 과거에 존재했는지 여부는 **미확인**으로 둡니다.

무규범 원칙 자체는 유효하되 근거는 아래 선례로 답니다. **성격이 다른 두 계열이므로 하나의
원칙으로 묶지 않습니다.**

**(가) 판정하지 않는 선례** — 결과에 평가를 얹지 않는다

- 전월세 전환율 계산기 — 상한 초과를 사실로만 표시, 위법 판정 없음
- 대환대출 계산기 — 유불리 판정 없이 두 관점 병렬 표시

**(나) 근거 없는 기본값을 두지 않는 선례** — 검증된 공통값이 없으면 상수화하지 않고 입력받는다

- 환전 계산기 — `src/lib/policy/currency.ts` 주석: *"당초 확장 계획에는 통화별 현찰 스프레드
  기본값을 두기로 되어 있었으나 … 스프레드는 상수화하지 않고 사용자에게 입력받습니다."*
  `supported` 밖 항목으로 *"은행별 현찰 스프레드 (검증된 공통값 없음 — 사용자 입력)"* 을 명시

비상자금의 **대비 개월 수**는 (나)에 해당합니다. 사이트가 권장 개월을 제시하지 않는 이유는
그 값을 평가로 보기 때문이 아니라, **검증된 공통값이 없기 때문**입니다.
5.1절의 소득 대비 지출 비율 무평가는 (가)에 해당합니다. 두 규율은 연결되지만 같지 않습니다.

## 11. 대표 사용자 흐름 (2026-09-16 실측 기준)

모든 계산기에 생활 사건을 붙이지 않습니다. 아래 4개는 실제 구현으로 확인되는 대표 흐름입니다.

### 흐름 A — 집을 산다 (현행 유지)

| 항목 | 내용 |
|---|---|
| 생활 사건 | 주택 매수 |
| 사용자 질문 | 얼마나 빌릴 수 있고, 현금은 얼마가 필요하며, 수익은 나는가 |
| 공식 근거·가정 | LTV 비율표·절대한도·방공제 / 지방세법 취득세 / 공인중개사법 매매 중개보수. 등기비용은 사용자 입력(국민주택채권 할인율 일 단위 변동) |
| 입력 | 주택가격·지역·주택수·선순위 → 매매가·보유수·조정지역 → 월세·대출이자 |
| 담당 계산기 | `/dsr-calculator` · `/ltv-calculator` → `/real-estate/initial-cost-calculator` → `/real-estate/property-yield-calculator` |
| 결과 범위·한계 | 담보 기준 추정 한도. 금융회사 심사·소득 인정방식 미반영 |
| 다음 행동 | 금융회사 한도 조회, 중개·법무 견적 |
| 연결 필요 | Decision 내부 인계로 충족. Knowledge 연결 불필요 |

**상태: 잘 작동합니다.** `handoff.ts` 가 값을 인계하고 홈 `MONEY_FLOW` 4단계가 같은 순서를 노출합니다.

### 흐름 B — 이사한다 (현재 끊김 → 자금계획이 채움)

| 항목 | 내용 |
|---|---|
| 생활 사건 | 전·월세 이사, 임차 계약 |
| 사용자 질문 | 이사를 실행하려면 추가 현금이 얼마 필요한가 |
| 공식 근거·가정 | 임대차 중개보수는 `policy/brokerage.ts` 에서 **`unsupported`**. v1 직접 입력 |
| 입력 | 새 보증금 · 기존 보증금 회수액 · 이사비 · 중개보수 · 가전·가구 · 기타 |
| 담당 계산기 | **없음** → 자금계획 이사자금 계산기 |
| 결과 범위·한계 | 보증금 회수 **시점**(기존 계약 종료와 새 계약 잔금의 시차)은 계산하지 않음. 금액만 다룸 |
| 다음 행동 | 부족분이 있으면 전세대출 한도 확인 |
| 연결 필요 | `/jeonse-loan-calculator` · `/real-estate/jeonse-vs-wolse-calculator` 와 상호 링크 |

**상태: 공백입니다.** 전세대출·월세 vs 전세·전월세 전환율·공실률 4개는 **계약 조건**을 다루고,
"이사 실행에 필요한 현금"을 계산하는 페이지는 없습니다.

### 흐름 C — 소득이 끊긴다 (현재 없음)

| 항목 | 내용 |
|---|---|
| 생활 사건 | 퇴사·휴직·이직 공백 |
| 사용자 질문 | 얼마를 모아둬야 하고, 지금 자금으로 몇 달 버티는가 |
| 공식 근거·가정 | 없음(순수 산술). 실업급여·정부지원금은 v1 제외 — 0.3절 Step 3 충돌 대상 |
| 입력 | 월 필수지출 · 대비 개월(사용자 결정) · 현재 사용 가능한 자금 |
| 담당 계산기 | **없음** → 자금계획 비상자금 계산기 |
| 결과 범위·한계 | 대비 개월은 사이트가 권장하지 않음. 소득 재개 시점·퇴직금·실업급여 미반영 |
| 다음 행동 | 부족분을 월 잉여자금·목표 저축으로 이어 계획 |
| 연결 필요 | `/finance/goal-savings` 링크. **값 인계 없음**(goal-savings 는 현재 보유자금 입력이 없음 — 3.2절) |

### 흐름 D — 목돈을 모은다 (현행 유지)

| 항목 | 내용 |
|---|---|
| 생활 사건 | 목표 저축 (전세보증금·차량·학자금 등) |
| 사용자 질문 | 언제까지 얼마를 넣어야 하는가 |
| 공식 근거·가정 | 없음(순수 산술). 기말 납입 월복리, 세전 |
| 담당 계산기 | `/finance/goal-savings` (3모드) |
| 결과 범위·한계 | **현재 보유자금 미반영**(3.2절). 세금·우대금리·중도인출 미반영 |
| 연결 필요 | 자금계획 월 잉여자금 → 목표 저축 링크 |

**상태: 기존 계산기가 담당합니다.** 자금계획에 복제하지 않습니다.

**(나) 취득세 기준일이 정책 메타와 연동되어 있지 않습니다**

정책값을 갱신해도 화면 날짜는 그대로 남습니다. 전월세 전환율이 `getLegalConversionCapPct()`

→ `formatPolicyStamp(meta)` 로 파생시키면 사람이 지키는 규칙이 아니라 구조로 강제됩니다.

**(다) 홈에 가이드(`/blog`) 진입 동선이 없습니다**

`homeNav.ts` 의 `CALC` · `PURPOSE_GROUPS` · `MONEY_FLOW` · `CATEGORY_HUBS` 어디에도 `/blog`
링크가 없습니다. Header 에는 "금융 가이드" 그룹이 있습니다. SOP-001 의 Decision Handoff 는
계산 뒤 절차로 잇는 흐름인데, 홈에서는 그 반대 방향 진입점이 비어 있습니다.
→ 노출 위치 변경은 별도 판단이 필요하므로 **이 문서에서 확정하지 않습니다.**

**(마) 일반 입력 오류에서 결과가 함께 보인다 — 배포 전 처리 대상**

`hasFieldError` 로 결과를 차단하는 것은 현재 **자금계획 3종에만** 적용되어 있습니다.
나머지 26개 계산기는 상한 초과 같은 `validate` 오류가 표시된 상태에서도 그 값으로
계산한 결과를 함께 보여 줍니다. 거부된 입력(허용되지 않은 문자)은 전 계산기에서
차단되지만, 검증 오류는 아직 차단되지 않습니다.

→ **처리 완료 (2026-09-16).** 단일 모드 21개는 `hasFieldError(state)` 로 전환하고,
모드·조건부 입력이 있는 7개는 `hasFieldErrorIn(state, 활성 키)` 로 **화면에 보이는
입력만** 보도록 했습니다. 숨겨진 비활성 모드의 오류가 현재 모드의 계산을 막지
않습니다.

**(라) 공개 가이드의 판정 표현** — 기존 후속 검토 항목으로 유지합니다.
`blogPosts.ts:904`(`jeonse-vs-wolse`, 공개) 등에 "유리하다" 표현이 있습니다. 표현이 존재한다는
