## 1. 확정된 제품 방향

| 항목 | 결정 |
|---|---|
| 성장 방식 | **신규 사이트 생성이 아니라 머니계산기 확장이 1순위** |
| 주제 포함 판정 | **"핵심 입력값이 돈인가, 물건인가"** — 돈이면 머니계산기, 물건·행정정보면 제외 |
| 신규 소비자 계산기 사이트 | 만들지 않음 |
| 확장 축 | 부동산 **금융**(대출 한도·자금 조달·임대 수익)과 환전 |

이 방향의 실무적 의미는 두 가지입니다.

1. 부동산이라는 카테고리를 통째로 들여오는 것이 아니라, **부동산 거래에서 돈이 움직이는 지점만** 가져옵니다.
2. 이미 8개월치 계산기가 쌓인 코드베이스 위에 얹는 작업이므로, **새로 만드는 것보다 기존 엔진·컴포넌트 재사용률이 높은 순서**가 실행 순서를 정하는 주요 기준이 됩니다.

### 3.7 코드에 기록된 알려진 함정 (신규 계산기가 반드시 피해야 함)

`useCalcState`가 반환하는 `getWon()` / `getNum()`은 `useEffect`로 한 박자 뒤에 갱신되는 `latestStateRef`를 읽습니다. 그래서 **마지막 입력 시점에 stale 값**이 잡힙니다.
`fix(dsr): 마지막 입력 즉시 계산되도록 반응성 수정`, `fix(calc): 대출 3개 계산기 반응성 수정`, `fix(calc): 금융 4개 계산기 반응성 수정` — 같은 버그로 세 번 커밋이 나갔습니다.

현재 우회 방식(`DsrCalc.tsx`가 채택):
```
const won = (key: string) => { const n = Number(state[key]?.raw ?? "0"); return isNaN(n) ? 0 : n * 10_000; };
const num = (key: string) => { const n = Number(state[key]?.raw ?? "0"); return isNaN(n) ? 0 : n; };
```
즉 `useMemo` 안에서는 **현재 렌더의 `state[key].raw`를 직접 읽어야** 합니다.
같은 헬퍼가 여러 계산기에 복붙되어 있으므로, 8절에서 공통화를 제안합니다.

> **PR 0 실측 (2026-08-25)**: 이 함정은 과거형이 아니라 **당시 운영 중인 버그**였습니다.
> 24개 계산기 중 19개는 각자 로컬 헬퍼로 우회하고 있었지만, **5개는 그대로 stale 값을 쓰고
> 있었습니다** — 취득세·부동산 수익률·월세 vs 전세·전세대출·재건축 분담금.
> 실브라우저 확인 결과 취득세 계산기에 5억을 입력하면 **550,000원**(정답 5,500,000원의 1/10)이
> 표시되고 시간이 지나도 교정되지 않았으며, `?price=50000` URL로 직접 들어가면 결과가 아예
> 표시되지 않았습니다. ESLint 도 같은 지점을 `react-hooks/exhaustive-deps` 경고 5건으로
> 가리키고 있었습니다(useMemo 가 deps 의 `state` 를 실제로 읽지 않았기 때문).
> PR 0 에서 5개 모두 `readNum`/`readWon` 으로 교체해 해소했습니다.

기타 관례:
- 금액 입력 단위는 **만원**. 내부 계산은 원. (`kind: "money" | "integer" | "decimal"`)
- 금리 `0%`는 유효 입력이므로 truthy 검사 금지 — `(state.rate?.raw ?? "") !== ""`로 판정.
- `formatUnit()`은 억/만 단위로 축약, `formatKRW()`는 원 단위 전체 표기.

### 4.1 전세·월세를 새로 만들지 않는 이유

원칙("겹치면 억지로 페이지 수를 늘리지 말고 검색 의도와 사용자 흐름 기준으로 판단")을 적용한 결과입니다.

현재 4개 계산기는 검색 의도가 **이미 서로 다르게** 나뉘어 있고, 코드 주석에도 그 구분이 명시되어 있습니다.

| 계산기 | 사용자 질문 | 겹치지 않는 근거 |
|---|---|---|
| 전세대출 | "보증금 3억이면 대출 얼마 나오고 이자 얼마?" | 대출 상품 관점 |
| 월세 vs 전세 | "둘 중 뭐가 싼가?" | 기회비용 비교 |
| 전월세 전환율 | "이 전환이 법정 상한 안인가?" | 코드 주석: *"calcJeonseVsWolse와 역할이 다르다"* |
| 공실률 영향 | "공실 나면 수익 얼마나 깎이나?" | 코드 주석: *"calcPropertyYield의 공백을 채운다"* |

### 5.1 LTV 계산기 🟢 신규

| 항목 | 내용 |
|---|---|
| **사용자 목적** | 담보(주택) 기준으로 대출이 얼마나 나오는지 확인. DSR이 **소득 기준 한도**라면 LTV는 **담보 기준 한도**이며, 실제 한도는 두 값의 낮은 쪽이다. 현재 사이트는 소득 축만 있고 담보 축이 비어 있다. |
| **URL** | `/ltv-calculator` (대출 그룹은 루트 평면 경로가 관례) |
| **페이지 제목** | `LTV 계산기 — 주택담보대출 담보 기준 한도` |
| **아이콘** | 🏦 또는 📐 |

**입력값과 단위**

| 필드 | kind | 단위 | 비고 |
|---|---|---|---|
| 주택 가격(담보 평가액) | `money` | 만원 | 필수 |
| 지역 구분 | 토글 | — | 규제지역 / 수도권 비규제 / 지방 — **정책 테이블이 요구하는 축에 맞춰 확정** |
| 주택 보유 수 | 토글 | — | 무주택 / 1주택(처분조건 포함 여부) / 다주택 |
| 생애최초 여부 | 토글 | — | 우대 LTV 적용 대상 |
| 방공제 적용 | 토글 | — | 적용 / 미적용(MCI·MCG 가입) |
| 방공제 지역 | 토글 | — | 최우선변제금이 지역별로 다름 |
| 선순위 채권·임차보증금 | `money` | 만원 | 선택. 기존 근저당·전세보증금 |

**출력값**

- 적용 LTV (%) — 어떤 조건 조합으로 이 값이 나왔는지 함께 표기
- LTV 기준 담보 인정액 = 주택가격 × 적용 LTV
- 정책상 절대 한도 적용 여부 및 적용 후 금액
- 방공제 차감액
- 선순위 채권 차감액
- **최종 담보 기준 추정 한도**
- 필요 자기자금 = 주택가격 − 최종 한도
- 참고: 같은 조건에서 DSR 기준 한도도 확인하라는 안내 + `/dsr-calculator` 링크

**계산 공식**

```
담보인정액 = 주택가격 × 적용LTV(지역, 주택수, 생애최초, 가격구간)
절대한도 적용 = min(담보인정액, 정책상 절대 한도액)   ← 해당 정책이 있는 경우만
최종한도 = max(0, 절대한도 적용값 − 방공제액 − 선순위채권)
```

> ⚠️ **단일 고정 공식으로 단순화 금지.** `적용LTV`는 상수가 아니라 **(지역 × 주택수 × 생애최초 × 가격구간) → 비율** 을 반환하는 조회 함수여야 합니다. `dsr.ts`의 `getEffectiveStressRate()`와 동일한 형태입니다.

**필요한 정책·규제 데이터**

| 데이터 | 성격 | 출처(구현 시 원문 확인 필수) |
|---|---|---|
| 지역·주택수·생애최초별 LTV 비율표 | 수시 변동 (가계부채 관리방안마다 개정) | 금융위원회 보도자료, 은행연합회 공시 |
| 규제지역(조정대상지역·투기과열지구) 지정 현황 | 수시 변동 | 국토교통부 고시 |
| 정책상 대출 절대 한도액 | 수시 변동 | 금융위원회 |
| 방공제 = 소액임차보증금 최우선변제금 (지역별) | 개정 빈도 낮음 | 주택임대차보호법 시행령 |

> 이 문서는 **정책 수치를 확정해 적지 않습니다.** 착수 시점에 위 출처 원문으로 확인해 `src/lib/policy/ltv.ts`에 `verifiedAt`과 함께 기록하는 것이 이 계산기의 실제 작업 대부분입니다. 근거 없는 수치를 코드에 넣는 것이 이 계산기에서 가장 큰 위험입니다.

**데이터 기준일 표시 및 갱신**

- 결과 하단에 `기준일: YYYY-MM-DD · 출처: …` 고정 표기 (필수)

**예외 상황과 검증 규칙**

### 5.2 부동산 실투자금 계산기 🟢 신규

| 항목 | 내용 |
|---|---|
| **사용자 목적** | "매매가 6억이면 현금 얼마 있어야 하나." 매매가만 보고 자금 계획을 세우면 취득세·중개보수·등기비용이 빠진다. 기존 `property-yield-calculator`가 **자기 페이지에서 명시적으로 비워둔 공백**을 정확히 메운다. |
| **URL** | `/real-estate/initial-cost-calculator` |
| **페이지 제목** | `부동산 실투자금 계산기 — 취득세·중개보수 포함 총 필요자금` |
| **아이콘** | 💰 |

**입력값과 단위**

| 필드 | kind | 단위 | 비고 |
|---|---|---|---|
| 매매가 | `money` | 만원 | 필수 |
| 주택 보유 수 | 토글 | — | `OwnershipType` 재사용 (first/second/third/fourth_plus) |
| 조정대상지역 | 토글 | — | 취득세 중과 판정 |
| 전용 85㎡ 초과 | 토글 | — | 농어촌특별세 과세 기준 |
| 대출금 | `money` | 만원 | 선택. LTV 계산기에서 쿼리로 인계 가능 |
| 임대보증금 | `money` | 만원 | 선택. 갭투자·임대승계 |
| 중개보수 | 자동/직접 토글 + `money` | 만원 | 자동 = 요율표 상한, 직접 = 실제 협의 금액 |
| 등기·법무 비용 | `money` | 만원 | 선택. 기본은 직접 입력 (아래 주석 참조) |
| 기타 비용 | `money` | 만원 | 선택. 이사·수리 등 |

**출력값**

- 취득세 · 농어촌특별세 · 지방교육세 · **취득세 합계** (기존 `calcAcquisitionTax` 결과 그대로)
- 중개보수 (자동 산정 시 적용 요율·한도액 함께 표기)
- 등기·법무 비용, 기타 비용
- **총 부대비용** 및 매매가 대비 비율(%)
- **총 필요자금** = 매매가 + 총 부대비용
- **실투자금(자기자금)** = 총 필요자금 − 대출금 − 임대보증금  ← 하이라이트
- 참고: 기존 수익률 계산기로 이어지는 링크

**계산 공식**

```
취득세합계   = calcAcquisitionTax(매매가, 주택수, 조정지역, 85㎡초과).totalTax   ← 기존 함수 재사용
중개보수     = min(매매가 × 상한요율(거래구간), 구간 한도액)                      ← 자동 모드
총부대비용   = 취득세합계 + 중개보수 + 등기법무비용 + 기타비용
총필요자금   = 매매가 + 총부대비용
실투자금     = 총필요자금 − 대출금 − 임대보증금
부대비용비율 = 총부대비용 ÷ 매매가 × 100
```

**필요한 정책·규제 데이터**

| 데이터 | 성격 | 현재 상태 |
|---|---|---|
| 주택 취득세율 (1주택 구간 누진, 중과, 농특세, 지방교육세) | 세법 개정 시 변동 | ✅ **이미 구현·검증됨** — `realEstate.ts`, 2026-08-02 지방세법 기준 |
| 중개보수 상한요율표 (매매/임대차, 거래금액 구간별, 한도액) | 개정 빈도 낮음 | ❌ 신규 필요. 출처: 공인중개사법 시행규칙 별표 — **지자체 조례로 세부가 달라질 수 있음을 고지** |
| 국민주택채권 매입률·즉시매도 할인율 | **일 단위 변동** | ❌ v1에서 **자동 계산하지 않음** (아래 참조) |

> **등기비용을 자동 계산하지 않는 이유**: 등기 비용의 큰 축인 국민주택채권 할인율은 매일 바뀌고 공신력 있는 정적 소스가 없습니다. 매일 바뀌는 값을 정적 사이트에 상수로 박으면 그날부터 틀린 계산기가 됩니다. v1은 **사용자 직접 입력 + 개략 범위 안내**로 처리하고, 안내 문구에서 "법무사 견적 기준" 임을 명시합니다.

**데이터 기준일 표시 및 갱신**

- 취득세: 기존 검증일(2026-08-02) 승계, 결과 하단 표기
- 중개보수: 요율표 기준일 + "지자체 조례에 따라 다를 수 있음" 병기
- 갱신 트리거: 지방세법 개정(취득세), 공인중개사법 시행규칙 개정(중개보수)

**예외 상황과 검증 규칙**

| 상황 | 처리 |
|---|---|
| 실투자금 ≤ 0 | **정상 표시하되** "대출금과 보증금 합이 총 필요자금을 넘습니다 — 입력을 확인하세요" 안내. `PropertyYieldCalc`의 `isInvestedNegative` 패턴 재사용 |
| 대출금 > 매매가 | `InputField` `error` 표시 |
| 매매가 미입력 | 결과 미표시 |
| 중개보수 자동 모드에서 구간 경계 | 요율표 구간 경계 처리를 테스트 케이스로 명시 |

**기존 계산기와 공유할 수 있는 요소**

**확장 후보 중 재사용률이 가장 높습니다.** `calcAcquisitionTax`를 인자 그대로 호출하므로 취득세 로직을 다시 짤 필요가 없고, 취득세 계산기와 입력 축(주택수·조정지역·85㎡)이 완전히 동일합니다.

- 의도: "집 살 때 현금 얼마 필요한가" — 매수 검토 초기~중기
- 내부 링크(계산기): 취득세 계산기 / LTV 계산기 / 부동산 수익률 계산기 / 전세대출 계산기

### 5.4 환전 계산기 🟢 신규

| 항목 | 내용 |
|---|---|
| **사용자 목적** | "100만원 환전하면 달러 얼마 받고 수수료 얼마 떼나", "환율우대 90%면 얼마 아끼나". 매매기준율이 아니라 **현찰 살 때 환율 + 우대율**이 실제 지불액을 정한다. |
| **URL** | 8절/11절의 배치 결정에 따름 (`/finance/exchange` 또는 `/exchange-calculator`) |
| **페이지 제목** | `환전 계산기 — 환율우대 적용 실제 환전 금액` |

**입력값과 단위**

| 필드 | kind | 단위 |
|---|---|---|
| 환전 방향 | 토글 | 원화 → 외화 / 외화 → 원화 |
| 통화 | 토글/셀렉트 | USD, JPY, EUR, CNY … |
| 금액 | `money` | 원 또는 해당 통화 |
| 매매기준율 | `decimal` | 원 |
| 현찰 스프레드 | `decimal` | % (통화별 기본값 제시, 수정 가능) |
| 환율우대율 | `decimal` | % (0~100) |

**출력값**: 적용 환율 / 받는 금액 / 지불 금액 / 환전수수료 총액 / 우대로 절약한 금액 / 우대 0% 대비 차이

**계산 공식**

```
현찰살때  = 매매기준율 × (1 + 스프레드/100)
적용환율  = 매매기준율 + (현찰살때 − 매매기준율) × (1 − 우대율/100)
지불원화  = 외화금액 × 적용환율
수수료    = (적용환율 − 매매기준율) × 외화금액
절약액    = (현찰살때 − 적용환율) × 외화금액
```
(외화 → 원화는 `현찰팔때 = 기준율 × (1 − 스프레드/100)`로 부호 반전)

**필요한 데이터 — 이 계산기의 유일한 난점**

환율은 실시간 데이터이고, **현재 사이트는 전 페이지 정적 생성**입니다. 세 가지 선택지가 있고 각각 비용이 다릅니다.

| 안 | 방식 | 장점 | 비용·위험 |
|---|---|---|---|
| **A. 사용자 직접 입력** | 매매기준율을 사용자가 은행 앱에서 보고 입력 | 인프라 변경 0, 정적 유지, 값이 틀릴 위험 없음 | 입력 마찰 1단계 추가 |
| **B. 빌드타임 fetch + ISR** | 한국수출입은행 등 공개 API를 `revalidate`로 주기 갱신 | 사용자 마찰 없음 | 정적 전제 이탈, API 키 관리, 배포 인프라 확인 필요, 장애 시 오답 노출 |
| **C. 클라이언트 fetch** | 브라우저에서 직접 호출 | 항상 최신 | CORS·키 노출·rate limit, 정적 사이트에 부적합 |

**권장: v1은 A안.** 이유 — (1) 인프라를 건드리지 않아 이번 확장 범위 안에 들어옴, (2) 이 계산기의 사용자 질문은 "지금 환율이 얼마냐"가 아니라 "**우대율을 적용하면 얼마 아끼냐**"이므로 기준율은 입력값이어도 효용이 유지됨, (3) 틀린 환율을 자동으로 보여주는 것보다 사용자가 넣은 값으로 계산하는 쪽이 신뢰 위험이 낮음.
→ **최종 결정은 11절 질문 Q3.**

**기준일 표시**: A안에서는 "입력하신 기준율 기준 계산" 문구 + 통화별 스프레드 기본값의 기준일·출처 표기.

**예외**: 우대율 > 100% 또는 < 0 → `error`. 기준율 0 이하 → 결과 미표시. 금액 0 → 미표시. JPY는 100엔 단위 고시라는 점을 **반드시** 반영(가장 흔한 계산 오류).

**재사용**: `CalcShell` `InputField` `ResultCard` `useCalcState` — UI는 전부 재사용. 계산 엔진은 신규(`lib/exchange.ts`).

**SEO**: 의도는 "환전 수수료 아끼는 법 / 환율우대 계산". 기존 계산기 중 직접적 연결 대상이 적어 **내부 링크 관점에서 고립되기 쉬움** — 실질금리·인플레이션 계산기와 "돈의 실질 가치" 축으로 묶는 것이 현실적.

**난이도 하(A안) / 정책 변경 위험 없음 / 데이터 신선도 위험 최상**

### 5.5 부동산 자금 동선 연결 🔵 보강 (신규 페이지 없음)

세 계산기를 **하나의 흐름**으로 잇습니다.

```
LTV 계산기            "얼마 빌릴 수 있나"      → 대출금
   ↓ 쿼리스트링 인계
실투자금 계산기        "현금 얼마 필요한가"     → 실투자금
   ↓ 쿼리스트링 인계
부동산 수익률 계산기    "그래서 수익 나나"
```

`useCalcState`가 이미 URL searchParams와 양방향 동기화하므로, **"이 값으로 다음 계산기 열기" 링크 한 줄**로 구현됩니다. 새 인프라가 필요 없습니다.
동시에 DSR ↔ LTV를 "소득 기준 한도 ↔ 담보 기준 한도"로 상호 링크해 두 축을 완성합니다.

평가 기준 6개를 5점 척도로 매겼습니다. **유지보수 부담은 낮을수록 높은 점수**(부담이 적을수록 좋음)입니다.

| 작업 | 주제<br>적합성 | 검색 의도·<br>사용자 효용 | 코드<br>재사용성 | 공식 정확성<br>구현 가능성 | 유지보수<br>(높을수록 부담 적음) | 기반<br>기능성 | 합계 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| **0. 공통화 (ToggleGroup·policy·state 유틸)** | — | — | 5 | — | 5 | **5** | **기반** |

### 6.1 점수만 따르지 않는 이유 — 권장 실행 순서

합계로는 실투자금(25)이 LTV(24)보다 높지만, **권장 순서는 LTV가 먼저**입니다.

- **입력 축을 LTV가 정의합니다.** LTV와 실투자금은 지역·주택 수·조정대상지역이라는 축을 공유합니다. 실투자금을 먼저 만들면 취득세 기준 축(주택수·조정지역·85㎡)만 반영되고, 나중에 LTV를 붙일 때 지역 구분 체계를 다시 손봐야 합니다.
- **실투자금은 LTV 결과를 인계받을 자리가 있습니다.** 반대 방향 의존은 없습니다.
- **기반 기능성이 명시적 평가 기준**입니다. LTV는 담보 기준 한도라는 축 자체를 사이트에 추가하는 유일한 항목입니다.

단, LTV는 **정책값 확정이 선행 조건**입니다(11절 Q1). 정책 확인에 시간이 걸려 착수가 지연될 경우, **실투자금을 먼저 진행하고 LTV를 뒤로 미루는 것도 유효한 대안**입니다 — 그 경우 실투자금의 지역 입력을 취득세 축(조정대상지역 여부)만으로 좁혀 두고, LTV 도입 시 확장하는 것으로 처리합니다.

`5. 자금 동선 연결`은 점수가 가장 높지만 **1·2가 존재해야 성립**하므로 마지막입니다.

스프레드는 은행·통화·상품·채널마다 다르고 검증된 공통값이 없습니다.
평균값을 심으면 사용자가 손대지 않았을 때 근거 없는 수수료가 조용히 계산에 들어갑니다.

그 파일에 남은 것은 **고시 단위 하나**입니다. 이건 추정값이 아니라 은행 고시 관행이고,

```
100단위 고시: JPY · IDR · VND · KHR   (근거 1차 — 은행 고시환율표)
1단위 고시  : 그 외
```

#### 계산식 (1차 확인)

```
현찰 살 때 = 매매기준율 × (1 + 스프레드율)
현찰 팔 때 = 매매기준율 × (1 − 스프레드율)
우대율 p   → 스프레드율 × (1 − p)
우대 100%  → 매매기준율 그대로
```

우대율은 **환율이 아니라 수수료를 깎는 비율**입니다. 이 오해가 흔해서 가이드·FAQ·
예시 note 세 곳에 같은 설명을 넣었습니다.

| 현찰 환율 미입력 (현찰 모드) | 위와 동일 |
| 현찰 환율과 매매기준율의 대소가 방향과 반대 | 두 값이 뒤바뀐 입력 |
| 목록에 없는 통화 | 고시 단위를 모른다 |

수익률을 함께 표시합니다.

| 부대비용 2,000만원 | 1억 2,000만원 | **4.00%** |

부대비용을 넣으면 실제로 나간 돈이 있으므로 0 초과가 되어 수익률이 계산됩니다.

### 8.2 정책 데이터 계층 `src/lib/policy/`

현재 정책값이 `dsr.ts`(상수 + 주석)와 `realEstate.ts`(`CONVERSION_RATE_INFO` 객체) **두 가지 다른 형태**로 흩어져 있습니다. 확장하면서 세 번째 형태를 만들지 않도록 하나로 정합니다.

```ts
// src/lib/policy/types.ts
export interface PolicyMeta {
  verifiedAt: string;      // "YYYY-MM-DD" — 원문을 직접 확인한 날짜
  source: string;          // 기관명 + 문서명
  sourceUrl?: string;
  note?: string;           // 유예·경과규정 등
  nextReviewHint?: string; // "지방 유예 종료 2026-12-31", "금통위 후 재확인"
}

export interface PolicyTable<TKey extends string, TValue> {
  meta: PolicyMeta;
  values: Record<TKey, TValue>;
  unsupported?: string[];  // 의도적으로 지원하지 않는 조합 (임의 보간 금지 표식)
}
```

배치:


##### ⚠️ `낮은 값`은 남긴다 — 산식 설명이라서

`낮은 쪽`(DSR·LTV 비교)과 `낮은 값`(min 산식)은 다릅니다. 아래는 **정상**입니다.

```text
LtvCalc.tsx           = 담보 기준 한도 (둘 중 낮은 값, 최소 0)
ltv-calculator/page   담보 기준 한도 = 차감 후와 절대한도 중 낮은 값 (최소 0)
전월세 전환율 4곳      법정 상한 = 연 10%와 (기준금리 + 2%) 중 낮은 값
```

앞의 둘은 `차감 후 금액`과 `절대한도`에 `min()` 을 적용하는 산식이고,
전월세 쪽은 주택임대차보호법 제7조의2 의 법정 상한 산식입니다.
**규제 축 두 개를 비교하는 서술이 아닙니다.**

#### 계산기 개수를 적지 않는다

`27개`, 카테고리별 `10·7·10개`를 하드코딩했다가 제거했습니다. 전체 계산기를
한곳에서 세는 레지스트리가 없어, 계산기를 추가하면 그대로 낡습니다.
레지스트리가 생기면 그때 자동 산출해서 표기합니다.

#### 목적 그룹은 대표 CTA 하나

같은 크기 카드를 여러 개 두면 "무엇부터 눌러야 하나"를 사용자가 다시 고민하게
됩니다. 홈의 목적이 그 고민을 없애는 것이므로 그룹마다 **대표 CTA 1개 + 보조
링크**로 바꿨습니다.

| 그룹 | 대표 | 보충 안내 |
|---|---|---|
| 얼마나 빌릴 수 있는지 | **DSR 계산기** | 주택담보대출이라면 LTV 도 함께 확인 |
| 집을 사거나 임대 투자 | **실투자금 계산기** | 매매가만으로는 부족하다는 점 |
| 저축하고 현금 관리 | **목표 저축 계산기** | 목표·기간에서 월 납입액 역산 |

저축 그룹의 대표를 목표 저축으로 둔 이유는, 저축의 출발점이 "얼마를 모아야
하나"이기 때문입니다. 예·적금 이자 계산은 목표가 정해진 뒤의 단계입니다.

#### 목적별 영역은 3열 compact 카드

첫 구현은 목적 3개를 `max-w-5xl` 패널에 세로로 쌓고, 대표 CTA 를 블록 요소로
두었습니다. 그 결과 **파란 CTA 가 패널 폭 전체를 채워 버튼이 아니라 광고 배너처럼**
보였고, 같은 형태가 세 번 반복돼 "긴 배너 3개"가 됐습니다.

| | 처음 | 수정 후 |
|---|---|---|
| 영역 폭 | `max-w-5xl` | `max-w-4xl` (896px) |
| 배치 | 세로 3단 | 데스크톱 3열 · 모바일 1열 |
| 대표 CTA | 블록, 카드 폭 전체 | `inline-flex` **178px 버튼** |
| CTA 내용 | 제목 + 긴 설명 | `DSR 계산기로 시작 →` |
| 보조 링크 | 4~6개 | 3개 + 카테고리 허브 |
| 홈 전체 높이 | 4,474px | **3,618px** |

설명은 버튼 안이 아니라 버튼 위 본문에 둡니다. 카드가 269px 로 좁아지므로
그룹 제목도 한 줄에 들어가게 줄였습니다.

> **링크는 줄이지 않았습니다.** 문제는 링크 수가 아니라 그것을 담은 컨테이너가
> 너무 넓고 반복된 것이었습니다. 각 그룹에서 빠진 보조 계산기는 카드 하단의
> 카테고리 허브 링크로 이어집니다.

#### 남은 중복 4건은 의도한 것

`DSR·LTV·실투자금·수익률` 이 각각 2회 등장합니다. 목적별 카드(탐색)와 자금 흐름
단계(순서 설명)는 역할이 다르고, 자금 흐름은 이 사이트의 차별점이라 링크가 필요합니다.
개편 전 최대 5회에서 2회로 줄인 상태이며, 더 줄이려면 자금 흐름에서 링크를 빼야 하는데
그러면 단계별 진입이 막힙니다.

#### 값 인계 범위를 화면에 정확히 적었다

자동으로 다 이어지는 것처럼 보이면 안 되므로 단계마다 실제 동작을 적었습니다.

```text
1 DSR  → 2 LTV        입력값 이어지지 않음 (요구 입력이 겹치지 않아 넘길 값이 없음)
2 LTV  → 3 실투자금    주택가격·담보 기준 한도 인계
3 실투자금 → 4 수익률   매입가·대출·보증금·부대비용 인계
```

## 11. 미확정 사항 — 개발 착수 전 결정이 필요한 질문

### Q1. LTV 정책값을 누가, 어디까지 확정할 것인가 ⛔ **PR 1 착수 차단 요인**

LTV 계산기 작업의 대부분은 코드가 아니라 **정책 테이블 확정**입니다. 결정할 것:

1. **지역 구분 축** — 규제지역/비규제 2분법인가, 수도권/지방 축을 함께 쓰는가? (DSR은 `metro`/`local` 2분법을 씀 — 같은 축을 쓰면 코드가 일관되지만 LTV 정책이 요구하는 축과 다를 수 있음)
2. **v1 지원 범위** — 주택담보대출만? 생애최초·서민실수요자 우대까지? 처분조건부 1주택까지?
3. **방공제** — v1에 포함? 지역별 최우선변제금 테이블까지 넣을 것인가, "MCI 가입 시 미적용" 토글로 단순화할 것인가?
4. **정책 절대 한도** — 현행 한도 규정을 반영할 것인가, 반영한다면 어떤 조건에 적용되는지까지 분기할 것인가?

> 권고: `dsr.ts`가 v1을 "주담대 전용 · 변동/순수고정만 · 혼합형 미지원"으로 **좁게 자르고 나머지를 주석에 v2 스펙으로 남긴** 방식이 잘 작동했습니다. LTV도 같은 방식으로 **좁게 시작**할 것을 권합니다.

### Q2. 테스트 러너를 이번에 도입할 것인가

현재 테스트가 0건입니다. LTV·실투자금·환전은 경계값이 많아 회귀 위험이 기존 계산기보다 큽니다.

- **A안 — 도입하지 않음**: 이번 범위에 집중. EXAMPLES 수치를 손으로 검산해 회귀 기준으로 사용.
- **B안 — Vitest 최소 도입**: 신규 엔진 3개만 대상. devDependency 1~2개 추가. "불필요한 패키지 업그레이드 금지" 원칙과 충돌하지는 않으나 **범위 확대**임.

> 이 문서는 어느 쪽도 전제하지 않았습니다. 9.3절이 두 경우를 모두 기술합니다.

### Q3. 환전 계산기의 환율 데이터 (5.4절)

A(사용자 직접 입력) / B(빌드타임 fetch + ISR) / C(클라이언트 fetch) 중 선택.

### Q4. 환전 계산기를 어느 그룹에 넣을 것인가

현재 `/finance` 그룹은 예·적금·복리·인플레이션 등 **저축·자산 축**입니다. 환전은 여기에 완전히 들어맞지 않습니다.
